# 长跑批处理必须有看门狗与输入预检，发现挂死立即止损不观望

**问题描述**：2026-07-12 pt_batch.py 批处理流水在一个病态 Excel（sheet dimension 被撑到 104 万行）上空转 4 小时。主 Agent 在卡死 71 分钟时就发现异常并定位了根因，但只给了"建议修复"就停下等用户拍板，没有杀进程止损；直到 4 小时后用户查进度才发现还卡着。用户连续修正："死在这干嘛，加看门狗，搞不定就要退出，指定超时时间30分钟，并把这个文件隔离后面也不再读"、"你不是有20个进程，卡了20个？"、"一看超71W行就不要搞了 浪费我四个小时"、"纠正超过7W行直接跳过不搞了"。

**触发场景**：批处理流水设计时没有超时兜底，单个病态输入拖死整条流水线（并发进程全被同一文件占住）；主 Agent 监控后台任务时因"进程还活着、可能还在磨"而持续观望，已确认根因仍不动手。

**教训/建议**：
1. 长跑批处理任务必须有看门狗/超时兜底（单文件超时即杀、隔离该文件后续不再读），这在设计流水时就默认加上，不等事故后补——"一个输入不能拖死整条流水线"是批处理基本素养。
2. 输入侧廉价预检优于事后超时兜底：设计解析器时先问"什么样的输入是病态的、能不能一眼识别"，能一眼识别的直接跳过（本例：sheet dimension 超 7 万行不读），成本为零、止损在最前面。超时兜底是第二道防线，不是第一道。
3. 主 Agent 监控后台任务发现挂死迹象（日志停更超过已知最坏重试窗口、产出目录零增长）时，立即报告用户并给出止损动作（杀进程/隔离文件/重启），不许因"进程还活着"继续观望——本次 71 分钟时已确认根因，拖到 4 小时是纯损失。用户对"浪费时间"的容忍度远低于对"中断一个可恢复任务"的容忍度：流水线有 checkpoint，杀掉重启零成本，观望才是最贵的选项。
