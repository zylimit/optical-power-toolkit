# 生产删除前必须重查目标当前状态，归因必须有直接证据

**问题描述**：2026-07-07 生产部署验收期间，主 Agent 发现 sessions 表有一条 id=1「2026-7-7」（import_status=empty），凭「deployer 冒烟日志里有 POST /api/sessions 201」推断它是 deployer 冒烟残留，执行 DELETE /api/sessions/1 清理。实际该 Session 是用户本人刚创建的（用户已拿到密码登录生产系统），且删除时刻用户的真实全量 NCE zip 导入已开跑 46 秒（进度 40%）——DELETE 导致导入 worker 外键违例崩溃、级联清掉部分导入数据、前端轮询 404 假死，用户白等并报「崩溃了，连 Session 都没了」。

**触发场景**：部署验收时想清理疑似冒烟测试残留数据。根因两层：① 判定依据是几分钟前的旧快照 + 未经证实的归因——deployer 终报被 stop-hook 吞了（挂账 hook 缺陷 #14 ④ 的实害案例），主 Agent 没有拿到"这个 Session 是 deployer 建的"直接证据，只有时间相近的间接推断；② 执行删除前没有重新查询目标当前状态——当时 import_status 已是 running，查一下就能拦住。

**教训/建议**：对生产/共享环境做任何删除・停用・覆盖类写操作前：
1. 必须当场重新查询目标对象的最新状态，不允许拿本轮对话早些时候的快照当依据；
2. 归因必须有直接证据（创建者字段、审计日志、亲眼所见的创建动作），"时间上对得上"的推断不算；
3. 环境里可能有并发使用者（用户本人随时可能已登录在用），部署完成后 URL/凭据一旦可达，就要把系统当"已有真实用户"对待；
4. 吃不准就先问用户或只做只读核查——清理残留宁可留着也不误删。

关联：deployer 终报被 stop-hook 吞是已挂账 hook 缺陷 #14 ④——终报若在，主 Agent 本可从报告确认冒烟 Session 的处置状态。
