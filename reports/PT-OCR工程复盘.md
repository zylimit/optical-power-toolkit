## 四、五次生产事故与工程响应

### 事故① 病态 Excel 拖死流水线（07-13，损失 4 小时）
- **现象**：batch 在一个 9MB 的 xlsx 上静默空转 4 小时，零日志零产出。
- **根因**：该文件 sheet dimension 被撑到 `A1:AI1048576`（104万行×35列≈3670万单元格），纯正则解析陷入近似死循环；且抽取是主进程内函数调用，挂死无法强杀。
- **响应**：① 主防线——解析前只读 XML 头 4KB 取 dimension，**超 7 万行直接跳过**（病态样本实测 4 小时 → 0.55 秒）；② 兜底——抽取改子进程 + 单文件 30 分钟看门狗，超时自动改名 `.skip` 隔离永不再读。
- **黑色幽默**：事后发现该文件 0 行有效数据，4 小时纯属给垃圾陪葬。

### 事故② C 盘爆满杀死复核收尾（07-12，损失 52 个文件进度）
- **现象**：R1 收尾阶段连续 `No space left on device`，好在单文件事务全部安全回滚。
- **根因**：Codex CLI 把每次调用的完整会话（含图片数据）持久化到 `.codex/sessions`，**单日膨胀 20GB**，C 盘 200G 见底。
- **响应**：定期清理会话日志（累计清 40GB+）；根治方案（迁 D 盘/关持久化）留待办。

### 事故③ 并发拥堵制造假失败（07-12~13）
- **现象**：batch(20-30w) + recheck(10-15w) 同打一个 CLI 订阅，合计 35-40 并发后重试风暴，部分批次重试耗尽后**把清晰照片写成"OCR失败"**。
- **根因**：订阅 CLI 的吞吐天花板固定，加并发只会互相踩踏。
- **响应**：并发定档 10、两任务错峰；被冤枉的行进入嫌疑行清单事后翻案。

### 事故④ OAuth 断权污染库（07-14，327 行中毒）
- **现象**：R4 连续 21 个文件零抢救 + 242 行"清晰→OCR失败"。
- **根因**：Codex OAuth 过期，每次调用都失败，失败结果被如实入库；更阴的是复核行 model 被标成 codex，**会被复核队列的 model 过滤条件永久漏掉**。
- **响应**：止损杀进程 → 备份库 → 按 `ocr_at` 时间窗把 327 行 model 重置回队列；此后**每次启动前先跑真实 AUTH_OK 探针**，巡检加入"连续零抢救=断权哨兵"自动止损。

### 事故⑤ 上班时间 VPN 窗口干扰（07-14）
- **现象**：R5 期间 VPN 误开，在途批次烧重试。
- **根因**：办公网络环境（代理/VPN 切换）与外网 CLI 长任务天然冲突。
- **响应**：叫停改约非工作时段跑；长任务默认排晚间窗口。

## 五、数据分析的三个关键洞察

### 洞察① "OCR失败"是工具信号，不是数据信号
945 行 codex 名下的"OCR失败"重跑后 **80% 直接翻案成功**（R8 leg+971/1213）。结论：**codex 对真实照片只有两种诚实结论——读出来、或"确实糊"；直接报失败的，几乎全是 CLI 层故障（拥堵/断权/超时）**。以后见到"模型名下成批失败"，先查基础设施再怀疑数据。

### 洞察② 重复文件是统计口径的头号污染源
198 组同名副本（MD5 全量核对 197 组逐字节一致）+ 127 个改名副本（`_(COMPLETED)` vs ` COMPLETED` 这种），合计灌了 **34,927 行重复记录**。去重后待复核队列从 1611 行/51 文件**坍缩到 686 行/22 文件**——之前的"硬样本大户" PZ（396 行）、Owode（118 行）整个消失，本就是副本的影子。**任何按文件聚合的统计，做之前先按内容哈希去重，否则一半功夫喂了影子。**

### 洞察③ 压缩 1024px 对识别率无伤，速度 4 倍
- 全分辨率基准（Mabushi 158 行）：leg 救回率 27.8%，box +0
- 压缩 1024px（R6+R8 共 1473 行）：leg 救回率 69%（含翻案红利），box 救回显著（+190）
- 严格说两组样本不同质，但方向明确：**糊照片的瓶颈在拍摄质量，不在传输分辨率**。1024px 已保住可判读信息，节省的是纯粹的传输与推理开销。已设为复核默认。

## 六、提炼的工程法则（血泪浓缩）

1. **长跑批处理必须有看门狗**——超时即杀、隔离该输入、继续队列。这是设计期默认项，不是事故后补丁。一个输入不许拖死整条流水线。
2. **输入侧廉价预检 > 事后超时兜底**——读 4KB 头部识别病态（dimension 超限），比等 30 分钟超时便宜一万倍。设计解析器先问："什么输入是病态的？能不能一眼识别？"
3. **断点粒度要诚实**——文件级事务保一致性是对的，但大文件重跑的代价要在队列排序时支付：**小文件优先，大块头末位**，被杀时损失最小。
4. **共享额度的并发是零和的**——订阅 CLI 吞吐固定，两任务加并发=互相制造重试。错峰 > 并行，10 并发跑通 > 40 并发风暴。
5. **失败写库前先问是谁的失败**——工具故障期写入的"数据失败"是慢性毒药（还会被过滤条件掩埋）。启动前探针验活、运行中哨兵监控"连续零成功"模式、事后按时间窗翻案，三道防线一个不能少。
6. **验收只认新鲜证据**——进程活着≠在干活（看 json 落地数增长）；日志静默≠卡死（看在途 CLI 派发时间）；子任务说"完成"≠正确（亲跑命令数失败数）。
7. **发现挂死迹象立即止损，不观望**——checkpoint 完备的系统里，杀掉重启近乎零成本，观望才是最贵的（4 小时陪葬的教训）。
8. **会话类日志是隐形的磁盘杀手**——每次 CLI 调用都留全量转录时，8 万次调用=40GB。上量前先算日志账。
